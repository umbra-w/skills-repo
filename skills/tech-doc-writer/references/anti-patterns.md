# 反模式

## 反模式 1：术语堆砌而不解释

**为什么坏**：读者无法理解专业术语的含义，无法建立正确的概念模型。

**更好的做法**：首次出现时简要解释，或添加术语表。

**参考文档示例**：Intel Agentic AI SDK 文档中对"端云协同（Edge-Cloud Collaboration）"和"Token"给出了定义。

## 反模式 2：没有上下文直接进入实现细节

**为什么坏**：读者不知道"为什么需要这个修改"，无法判断方案的合理性。

**更好的做法**：先说明需求背景和原理，再进入具体实现。

**参考文档示例**：4G 模块兼容方案文档先说明"为什么需要兼容"，再进入实现细节。

## 反模式 3：代码没有解释

**为什么坏**：读者看到修改但不知道修改意图，无法判断是否正确。

**更好的做法**：在代码块外添加说明，解释修改目的和逻辑。

## 反模式 4：结论没有证据

**为什么坏**：读者无法判断结论是否可靠。

**更好的做法**：提供 log、命令输出或测试结果作为证据。

## 反模式 5：假设伪装成事实

**为什么坏**：读者基于错误前提做出错误判断。

**更好的做法**：明确标注"推测""可能""需确认"。

## 反模式 6：章节之间逻辑跳跃

**为什么坏**：读者无法建立知识关联，容易迷失。

**更好的做法**：使用过渡句或过渡段连接内容。

## 反模式 7：无意义重复

**为什么坏**：增加文档长度但不增加信息量。

**更好的做法**：每个概念只解释一次，需要时引用。

## 反模式 8：过度抽象

**为什么坏**：读者无法将规则应用到实际问题。

**更好的做法**：提供具体示例和代码。

## 反模式 9：过度模板化

**为什么坏**：所有文档看起来一样但内容不匹配。

**更好的做法**：根据文档目的和读者选择结构，不机械套用。

## 反模式 10：一个段落承担多个逻辑任务

**为什么坏**：读者难以提取关键信息。

**更好的做法**：一个段落只讲一个主题。

## 反模式 11：用总结替代真正解释

**为什么坏**：读者只知道结论不知道推理过程。

**更好的做法**：展示推理链和证据。

## 反模式 12：领域默认假设误作通用规则

**为什么坏**：作者把自己的领域习惯（如"所有人都懂寄存器""所有人都用 C 语言"）当作默认假设，读者因缺乏前置知识而无法理解。

**更好的做法**：在写作前明确读者上下文，对非常见的前置知识进行说明或标注。

## 反模式 13：AI 味表达

**为什么坏**：看起来很多，实际上很浅，没有实质内容。

**表现**：
- 空洞总结："综上所述，这是一个复杂的问题"
- 模板化段落：每段都是"首先...其次...最后..."
- 过度编号：所有内容都编号，包括不需要编号的
- 泛泛而谈："这个方案有很多优点"
- 重复解释：同一个意思换几种方式说
- "看似完整、实际没有重点"

**更好的做法**：每个段落有实质内容，不为了凑篇幅而写。
## 反模式 14：口语化/拟人化比喻

**为什么坏**：用生动但不精确的比喻（"会被饿死""必要性就长这样"）替代精确描述，读者无法获得准确的技术理解。比喻在口头交流中有助于快速传达印象，但在技术文档中会模糊边界条件、因果链和工程判断依据。

**表现**：
- 拟人化："传感器会饿死""节点觉得痛"
- 口语化感叹："就长这样""就是这么简单"
- 过度文学化："活在两个世界拼起来的错觉里"
- 口号式简化："宁丢不凑""快就收紧，慢就放宽"

**更好的做法**：用精确描述替代生动比喻。把"为什么会这样"的完整链条写出来——条件、机制、中间状态、结果——而不是用一个拟人化的标签概括。例如：
- 坏："ApproximateTimeSynchronizer 在极端频率差下会被饿死"
- 好："ApproximateTimeSynchronizer 需要等齐三路才触发，但检测还没来的时候深度已经刷了 30 帧，队列塞满后开始丢帧，最终触发条件永远无法满足"

## 反模式 15：把写作步骤写进正文

**为什么坏**：作者把构思阶段的指导语原样输出到正文，例如"先理解 X 由哪几部分组成""先建立这个模型""我们来看"。这类句子不提供技术信息，只要求读者按作者的节奏组织理解。正文应直接给出结构与事实，读者能否形成模型是阅读结果，不是作者可以命令的动作。

**表现**：
- "先理解 repo 由哪三部分组成，所以先建立这个模型"
- "我们来看""下面介绍""接下来我将说明"
- "本篇将带你了解""读完你能掌握"
- 把 Step 9 的心智模型设计说明直接写进正文

**更好的做法**：删掉指导语，从事实开始陈述。需要交代范围时用一个短句说明内容，而不是描述读者的认知动作。例如：
- 坏："先理解 repo 由哪三部分组成，后面几乎所有报错都能归结到这三者，所以先建立这个模型。"
- 好："repo 由 launcher、repo 工具、manifest 三部分组成。"（后面直接接结构图，不加引导句）

## 反模式 16：把过程记录当成交付物

**为什么坏**：作者把工作过程原样输出，包括时间线、逐条命令、排查顺序和"我检查了 X 发现 Y"的叙述。读者需要的是能直接使用的结果，过程只对作者有价值。这类文档篇幅长，但可执行内容少，读者必须自己从叙述里提取结论。

**表现**：
- 按时间排列的排查记录："19:57 进程卡住，21:21 配置凭据，21:35 换 launcher"
- 命令流水："先跑 A 看到 B，然后跑 C"
- 逐个否定候选原因再给结论，而读者只想知道最终该做什么
- 附录堆诊断过程，没有可复用的操作步骤

**更好的做法**：把过程压缩成结论，只保留读者需要执行的部分。过程本身有价值时单独成文，标题写明是记录，并在开头给出结论，不与教程混写。

| 过程记录写法 | 交付物写法 |
|---|---|
| 19:57 看到 8 个进程卡住，`ss` 没有连接，判断是认证 | 认证未配置时 `repo sync` 会卡在等待输入，`.repo` 零增长 |
| 先试 A 不行，又试 B 也不行，最后 C 成功 | 用 C；A 和 B 在 Python 3.6 下不可用 |
| 21:25 删掉 `.repo/repo` 之后开始报错 | 不要删除 `.repo/repo`，缺失时 launcher 会重新初始化并失败 |

## 反模式 17：写未验证的变体，用绝对化结论收尾

**为什么坏**：文档里出现没有实际执行过的路径，例如另一个清单、另一个分支、另一种启动方式。读者照做时无法判断结果是否可信，出问题也无法回溯。绝对化结论（"必然失败""一定不行"）在条件变化后会变成错误信息：某个旧工具在特定条件下是可用的，写成"必然失败"就把可用路径否掉了。

**表现**：
- 教程同时写了 A14 和 A16 两套命令，实际只跑过 A14
- "用 X 必然失败"，没有说明在什么条件下失败
- 给出未测试的参数组合，读者遇到问题无从判断

**更好的做法**：只写本次执行并验证过的路径。变体要么删掉，要么明确标注未验证。绝对化结论改成条件描述。

- 坏："用 `python3 $(which repo)` 必然失败。"
- 好："`.repo/repo` 已存在时 `python3 $(which repo)` 可用；首次初始化会触发老 launcher 的 bytes 缺陷。"
