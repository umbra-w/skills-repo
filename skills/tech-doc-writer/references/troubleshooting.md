# 排障

## 核心原则

排障文档必须强调"证据链"：每一步排查都必须说明"这个动作能证明什么"。

这是技术文档区别于普通经验分享的关键。

## 排障结构

### 标准结构

```
## 现象
（描述可观察的现象，包括错误信息、异常行为、复现条件）

## 可能原因（候选列表）
（按可能性排序，标注优先级 P0/P1/P2）

## 排查步骤
1. 假设 1：XXX
   - 验证命令（带参数说明）
   - 预期输出
   - 判断依据（如果输出是 X，说明原因是 1；如果输出是 Y，排除原因 1）

2. 假设 2：XXX
   - 验证命令
   - 预期输出
   - 判断依据

## 根因
（经过排查确认的根本原因）

## 修复
（解决方案和修改内容）

## 验证
（验证修复生效的方法和预期结果）
```

### 排查步骤的关键

每个排查步骤的"判断依据"是最重要的部分。它告诉读者：这个命令的输出意味着什么，如何根据输出继续排查。

## 区分事实与推断

- **事实**：有 log 或命令输出支撑的结论。例如："dmesg 输出显示 'OOM killed process'"
- **推断**：基于经验的判断，需要标注"推测""可能"。例如："推测是内存泄漏导致"
- **假设**：待验证的候选原因。例如："假设 limit 设置过小"

## 排查的思维方式

### 假设驱动

先列出候选原因列表，再给出验证命令。读者需要知道"查什么"再知道"怎么查"。

### 二分法

将可能的原因分为两类，设计一个验证来区分：
- 是 A 还是 B？
- 是软件问题还是硬件问题？
- 是配置问题还是驱动问题？

### 逐步排除

每验证一个假设，就排除一个可能性。缩小范围，直到找到根因。

## 参考文档中的排障示例

### TP 排障

```
TP无响应：
  - 检查I2C通信（i2cdump）、供电、复位信号
  - 确认中断触发方式与驱动配置一致
```

### Camera 排障

```
1. 查看驱动 sensor id 是否读到
   - 如果没有读到，排查 i2c 通信
   - 查供电、mclk、pwr、rst、i2c 波形
2. sensor id 有读到，排查驱动能否抓图
   - v4l2-ctl --list-devices
   - media-ctl -p -d /dev/media0
```

### 声卡排障

```
播放音频后 suspend 音频卡顿
现象：播放音频时 suspend，音频会卡顿在一小节循环
原因：CPU 停止工作 → DMA 仍在运行 → 缓冲区残留 → 硬件关闭
解决：在 suspend 前后解绑和绑定声卡
```

### 4G 模块排障

```
问题：模块识别到了联通卡，但拨号卡住
排查：发现 busybox 未安装，导致 udhcpc 无法执行
解决：安装 busybox udhcpc
```
