# 写作方法

## 核心原则

### 1. 先想清楚，再写

写作前必须完成：文档目的、读者、核心问题、已有知识、缺少知识、核心结论、概念依赖关系、关键因果关系、主线、支线、需要哪些例子、需要哪些代码、哪些内容不需要写。

### 2. 结构由意图驱动

文档结构由问题类型、读者知识水平、技术复杂度、证据类型、交付目的共同决定，不由固定模板决定。

### 3. 认知路径优先

每一节都服务于读者认知的逐步建立。章节顺序服从理解依赖，而非传统文章模板。

### 4. 深度可控

区分结论层、机制层、实现细节层。根据需求决定深入程度，不展开到源码级也不停留在口号。

### 5. 事实与推断分离

事实、推断、假设、经验必须明确标注。禁止把猜测包装成确定事实。

### 6. 可执行内容必须可复现

代码、命令、配置必须是读者可直接复制执行的。提供最小可运行片段，避免无关上下文。

### 7. 证据链完整

故障排查必须说明"这个动作能证明什么"。每一步都有判断依据。

### 8. 每段代码有职责

代码不是装饰。证明机制、给出最小实现、展示 API、验证理论、帮助复现、展示错误，必须明确信息职责。

### 9. 信息取舍

核心内容必须写清楚，辅助内容适量，扩展内容可压缩，与主题无关内容删除。禁止"既然知道就全部写出来"。

### 10. 写完必须改

初稿 → 结构检查 → 事实检查 → 解释检查 → 工程可用性检查 → 删除冗余 → 补充关键缺口 → 语言调整 → 最终稿

## 写作流程详解

### 接收任务阶段

1. 理解用户需求：文档类型、输入材料、交付标准
2. 确定文档目的：解决什么问题、读者读完能做什么
3. 识别目标读者：技术背景、领域熟悉度、信息密度需求
4. 提取可靠事实：从输入中提取可验证的信息

### 规划阶段

5. 建立核心问题：用一句话表述文档的核心
6. 建立概念依赖关系：X → Y → Z 的依赖链
7. 设计文档结构：基于依赖关系而非模板
8. 建立心智模型：读者需要理解的核心系统模型

### 写作阶段

9. 逐层解释：从结论到机制到细节
10. 加入代码/命令/示例：每个有明确职责
11. 检查逻辑正确性：因果、事实、工程

### 修改阶段

12. 读者理解检查：读者能否跟上
13. 删除冗余：不影响核心理解的都删除
14. 语言调整：消除 AI 味、模板化
15. 最终自检：对照质量清单逐项检查

## 深度控制

### 三层模型

- **Layer 1（结论）**：让读者快速知道答案。适合管理层、快速参考。
- **Layer 2（机制）**：解释为什么。适合需要理解原理的工程师。
- **Layer 3（实现细节）**：具体怎么实现。适合需要动手实现的开发者。

根据读者需求决定在哪一层停止。不要所有事情展开到源码级，也不要只停留在概念口号。

### 复杂系统分析

涉及复杂系统时，区分三条线：

1. **静态结构**：系统由什么组成，组件之间如何连接
2. **数据流**：数据在哪里产生、如何流动、如何被转换
3. **控制流**：谁触发谁、谁决定下一步、状态如何变化

必要时增加：
- **时间/生命周期**：什么时候发生
- **异常路径**：失败时怎么走

## 信息取舍

### 优先级分类

| 级别 | 说明 | 处理方式 |
|------|------|----------|
| 核心内容 | 主线必备，缺少则文档不完整 | 必须写清楚 |
| 辅助内容 | 帮助理解但不是必备 | 适量，不喧宾夺主 |
| 扩展内容 | 深入细节，部分读者需要 | 可压缩，标注为可选 |
| 无关内容 | 与主线无关 | 删除 |

### 判断标准

- 删除这一段后，核心理解是否受影响？如果不受影响，删除。
- 这一段是否回答了"读者为什么现在需要知道这个"？如果不能，删除或合并。
