# 代码与示例

## 代码的职责

代码在文档中承担以下职责之一，必须明确：

1. **证明机制**：展示代码行为，证明某个机制确实如此
2. **给出最小实现**：让读者能够快速复现或参考
3. **展示 API**：说明接口的使用方式
4. **验证理论**：用代码验证某个假设
5. **帮助复现**：让读者可以复现问题或结果
6. **展示错误**：展示错误代码和正确代码的对比

如果一段代码不承担以上任何职责，删除它。

## 代码展示规范

### 最小可运行示例

优先使用最小可运行示例，快速建立认知。避免粘贴整个文件。

### 最小关键片段

用于解释某个机制，只展示与当前讨论相关的部分。

### 完整示例

当上下文复杂、需要复现时使用完整示例，但标注哪些部分是核心。

### 代码后解释（三段式）

每段代码使用三段式解释：

1. **代码块前**：用一两句话说明这段代码解决什么问题、为什么需要它
2. **代码块内**：对关键行注入行内注释，解释为什么这样做（领域知识、设计意图、约束条件）
3. **代码块后**：用简短说明总结整体效果、行为或关键注意事项

禁止逐行翻译代码。读者能看懂语法，需要解释的是意图。

### 参考文档中的代码解释级别

参考文档（WiFi定频、TP调试、声卡驱动等）中的代码解释模式：

**模式1：代码块前说明 + diff 内行内注释**

```c
// 代码块前说明：修改国家码分组，将KR从Group25剔除，单独创建Group30
diff --git a/.../rlm_domain.c b/.../rlm_domain.c
@@ -308,7 +308,7 @@ static const uint16_t g_u2CountryGroup24[] = {
-	COUNTRY_CODE_BR, COUNTRY_CODE_SA, COUNTRY_CODE_KR
+	COUNTRY_CODE_BR, COUNTRY_CODE_SA  //将使用到相同信道资源的国家合并到一个Group中，后面定义使用到信道资源是根据Group编号来区分的，在这里可以看到韩国国家码是KR，与BR巴西、SA沙特阿拉伯在Group25中，为了实现定制频段需求，现将KR从原有Group剔除
};
```

**模式2：代码块前说明 + 代码块后总结**

```
代码块前：通过锁使系统灭屏后保持唤醒
代码块内：+    __pm_stay_awake(&gt9_wakeup_lock);//保持唤醒
代码块后："通过锁使系统灭屏后保持唤醒，不进入休眠。"
```

**关键点**：
- 行内注释解释 WHY（为什么这样改），而非 WHAT（这行代码是什么）
- 代码块后的总结描述整体效果，而非重复代码内容
- 行内注释可以很长（如 WiFi 定频文档中的多行注释），只要信息有价值

### 何时不需要代码

- 纯概念解释：用文字和图表更清晰
- 架构设计：用架构图更清晰
- 方案对比：用表格更清晰

不要因为"技术文档应该有代码"而机械地插入代码。

## 示例使用

### 示例的目的

示例用于消除抽象。当概念仅靠文字难以理解时，用具体案例把抽象概念落地。

### 示例的格式

```
抽象概念 → 具体输入 → 处理过程 → 具体输出
```

### 好示例的特征

- 与解释内容直接相关，不是装饰性案例
- 使用读者熟悉的场景
- 从简单到复杂逐步展开
- 展示输入和输出的对应关系

### 参考文档中的示例

- **WiFi 定频文档**：展示了完整的 diff 格式代码修改，每个修改都有意图说明
- **TP 调试文档**：展示了排查命令和预期输出，每个命令都有参数说明
- **声卡调试文档**：展示了多种方法（udev/hda-verb/acpid/驱动修改），每种方法都有示例和解释

## diff 格式

代码修改使用 diff 格式展示，包含：
- 文件路径（`--- a/...` 和 `+++ b/...`）
- 行号上下文（`@@ -308,7 +308,7 @@`）
- 修改内容（`-` 删除行，`+` 新增行）
- 修改说明（代码块外）

## 配置参数注释

当参数含义不直观时，使用行间注释：

```c
gt9xx@14 {
    compatible = "goodix,gt9xx";  // 驱动匹配字符串
    reg = <0x14>;                // I2C从设备地址
};
```

不要注释自明的代码（如 `i++`），只注释需要领域知识才能理解的参数。
