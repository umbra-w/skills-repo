# 结构决策

## 结构选择的本质

结构不是标题模板。结构是信息依赖关系的可视化。

如果读者不知道 X，就无法理解 Y，那么 Y 不能在 X 之前出现。

## 五类问题 → 认知路径

### 1. 原理问题

**目标**：理解系统如何工作

**认知路径**：概念 → 组成 → 工作机制 → 数据/控制流 → 关键细节 → 限制

**适用场景**：驱动开发指南、框架分析、系统原理

**示例参考**：参考文档中的 LCD 驱动框架文档、Yocto 项目文档

### 2. 故障问题

**目标**：定位和修复问题

**认知路径**：现象 → 已知事实 → 候选原因 → 验证 → 排除 → 根因 → 修复 → 验证

**适用场景**：排障指南、问题排查、异常定位

**示例参考**：参考文档中的 TP 调试排障、Camera 调试排障、suspend-resume 后 TP 失灵

### 3. 使用问题

**目标**：完成特定操作

**认知路径**：目标 → 环境 → 最小示例 → 参数 → 常见场景 → 常见错误

**适用场景**：操作指南、工具使用、配置教程

**示例参考**：参考文档中的 efibootmgr 工具使用、4G 模块拨号配置

### 4. 架构问题

**目标**：理解系统设计

**认知路径**：目标 → 约束 → 组件 → 关系 → 数据流 → 控制流 → 生命周期 → 关键设计取舍

**适用场景**：系统设计文档、架构分析、方案设计

**示例参考**：参考文档中的 Intel Agentic AI SDK 架构分析、GMS 移植文档

### 5. 对比问题

**目标**：做技术选型

**认知路径**：比较目标 → 比较维度 → 核心差异 → 适用条件 → trade-off → 选择依据

**适用场景**：方案对比、技术选型、版本差异

**示例参考**：参考文档中的 PulseAudio vs PipeWire 对比

## 结构设计原则

### 1. 每一节必须有明确职责

每一节必须回答至少一个明确问题。如果无法回答"读者为什么现在需要知道这个"，则删除或合并。

### 2. 章节顺序服从理解依赖

如果章节 B 需要概念 X，而 X 尚未解释，则要么提前解释 X，要么标注"请先了解 X"。

### 3. 禁止"介绍一些相关知识"

不服务于主线的知识放附录或引用。

### 4. 概念依赖关系优先

```
概念依赖链：X → Y → Z
章节顺序：先 X，再 Y，再 Z
```

如果 Z 在文档中是最重要的结论，但读者需要先理解 X 和 Y，则 X 和 Y 必须在 Z 之前出现。

### 5. 结构选择决策树

```
开始写作前：
├── 文档目的是什么？
│   ├── 解释原理 → 原理问题路径
│   ├── 定位问题 → 故障问题路径
│   ├── 完成操作 → 使用问题路径
│   ├── 理解设计 → 架构问题路径
│   └── 做技术选型 → 对比问题路径
│
├── 读者知识水平？
│   ├── 初级 → Layer 1 为主，选择性进入 Layer 2
│   ├── 中级 → Layer 2 为主，关键点进入 Layer 3
│   └── 高级 → 快速过 Layer 1，重点在 Layer 2 和 Layer 3
│
└── 技术复杂度？
    ├── 低 → 简短直接，结论优先
    ├── 中 → 标准结构，适当展开
    └── 高 → 先建立心智模型，再逐步深入
```

## 章节设计模板（参考，非固定）

以下结构是参考参考文档中的常见模式总结的，但不能机械套用。

### 驱动开发文档

概念 → 框架流程 → 关键数据结构 → 具体方法 → 验证

### 方案设计文档

需求理解 → 方案对比 → 代码分析 → 应用案例

### 系统集成文档

架构 → 分组件步骤 → 区域/版本差异 → 认证排查

### 问题修复汇总

问题列表（每个：现象 → 修改说明 → 参考）

### 排障文档

现象 → 可能原因 → 排查步骤（假设→验证→判断）→ 根因 → 修复 → 验证
