# Prompt library (原子 Prompt 库)

Ready-made micro-prompts mapped to the 7-stage loop. Use these when you need a specific produce or audit move and don't want to reinvent the wording. Adapted from the source materials (68-prompt PDF, Skill 执行规范, 5 阶段任务对照表).

Format: `【trigger】` when to reach for this prompt · `【produce/audit】` which track · body.

Placeholder convention: 【方括号】 marks user-provided variables. Never invent values for them — ask the user.

---

## Stage 1 — 选题 / 问题定义 / 阐释对象

### P1.1 头脑风暴选题 · 产出
**Trigger:** user says "我想做 X 方向，帮我想题目" · **Produce**
```
请你作为【研究领域】方向的资深 PI 与顶刊审稿人，围绕【核心问题/应用场景】生成不少于 5 个可投稿级研究选题。每个选题必须同时说明：
1) 回应了哪类真实科学问题或应用痛点；
2) 现有研究为什么尚未充分解决；
3) 可能使用的数据、模型、实验或访谈资源；
4) 预期创新点是理论、方法、数据、系统还是应用；
5) 三个月内可完成的最小可行版本 (MVP)。
最后用"科学价值 / 创新性 / 数据可获得性 / 方法可操作性 / 论文可写性"五个维度打 1–5 分，并推荐 1–2 个最值得推进的方向。
拒绝生成"用 AI 提升某某准确率"式口号题目。
```

### P1.2 问题压缩链 · 产出
**Trigger:** direction too broad · **Produce**
```
请用"背景趋势 — 关键矛盾 — 可研究问题 — 变量关系 — 可验证贡献"链条重新定义【初步方向】。
输出：
1) 把宽泛方向压缩成一个核心研究问题；
2) 明确研究对象、时间范围、场景边界和证据边界；
3) 指出哪些概念仍需限定；
4) 3 个不同聚焦程度的题目版本；
5) 每个题目最适合用什么证据回答。
```

### P1.3 SMART 化 · 产出
**Trigger:** user has a rough question · **Produce**
```
把【研究主题】改写成 3 个 SMART 研究问题（对象明确、变量可测量、方法可执行、结论可比较、时间范围可控制）。
每个问题附：数据来源、核心假设、主要指标、潜在混杂因素、适合的论文章节位置。
```

### P1.4 可行性 7 维打分 · 审计
**Trigger:** post-produce audit for Stage 1 · **Audit**
```
请你作为极其严苛的开题评审委员会主席，审查【产出的选题/方案】。请从以下 7 个维度进行 0–10 分打分并指出致命缺陷：
1) 数据可得性
2) 标注/材料获取成本
3) 计算资源 (若适用)
4) 方法复杂度
5) 实验/写作周期
6) 伦理风险
7) 发表风险

然后：
- 明确指出哪些结果缺失会导致论文站不住脚；
- 给出降低风险的"最低可行研究版本 (MVP)"替代方案；
- 输出验收结论（通过 / 部分通过 / 不通过）。
```

### P1.5 研究边界主动限定 · 产出
**Trigger:** worry about over-claim · **Produce**
```
为【研究主题】划定论文边界。请明确：
- 研究什么、不研究什么
- 为什么不研究这些
- 结论允许外推到什么范围、不允许外推到什么范围
输出一段适合放入引言末尾或方法开头的边界说明。
```

## Stage 2 — 文献 / 检索 / 材料 / 现有方法 / 理论谱系

### P2.1 关键词与检索式 · 产出 (empirical / methods / review)
**Trigger:** user is starting a literature search · **Produce**
```
围绕【研究问题】构建系统检索关键词体系。分别给出：
- 核心概念词
- 同义词
- 上位词
- 下位词
- 方法词
- 数据词
- 评价指标词
- 排除词
组合成适合【数据库名称，如 Web of Science / CNKI / Scopus / PubMed / Google Scholar】的布尔检索式。
每一组关键词说明它对应 PICO / PECO / SPIDER 中的哪一部分。
如果检索结果过多或过少，说明应如何调整精度。
```

### P2.2 PRISMA 筛选流程 · 产出 (review-heavy)
**Trigger:** systematic review · **Produce**
```
为【综述主题】设计 PRISMA 风格文献筛选流程：
- 数据库组合与检索时间
- 中英文关键词与布尔式
- 纳入 / 排除标准 (每一条都给出理由)
- 初筛 / 全文复筛 / 质量评价三级步骤
- 分歧仲裁规则
- 筛选记录表字段
- PRISMA 流程图 (文字版四框：identified / screened / eligible / included，含各阶段数量占位符)
```

### P2.3 文献证据矩阵 · 产出
**Trigger:** user has some literature and wants organization · **Produce**
```
把【文献列表/笔记】按以下字段构建文献分类矩阵：
作者年份 | 研究对象 | 数据规模 | 理论视角 | 方法 | 对照基线 | 评价指标 | 主要发现 | 局限 | 与本研究的关系

矩阵之后总结：
1) 已有共识
2) 主要争议
3) 方法上的不足
4) 对象/场景上的空白
5) 本研究最适合切入的空白类型 (事实/方法/理论/数据/评价/场景/阐释视角)

不要编造未提供的文献，也不要把不确定信息写成确定结论。
```

### P2.4 空白真假鉴别 · 审计
**Trigger:** user claims a research gap · **Audit**
```
判断以下"研究空白"是否是真实空白：【空白描述】。
逐条检查：
1) 是"研究较少"这类伪空白，还是"存在但未被解决"的真实空白？
2) 已有研究做到什么、没做到什么？(具体到方法、指标、场景、对象)
3) 空白是否与研究问题的核心重要性直接相连？
4) 属于哪一类空白：事实 / 方法 / 理论 / 数据 / 评价 / 场景 / 阐释视角？
5) 是否足以支撑一篇论文？(而非只支撑一篇 short note)

若为伪空白，请重写为可辩护的空白陈述。
```

### P2.5 综述逻辑结构审计 · 审计
**Trigger:** user has a lit-review draft · **Audit**
```
审查【综述草稿】。硬指标：
1) 结构是否为"主题句 — 证据比较 — 不足分析 — 引出本文"？还是"张三说 X、李四说 Y"式罗列？
2) 每段是否有中心句和过渡句？
3) 引文是否服务于本文的空白与贡献，还是走马观花？

若失败，选一段重写为示范结构，并标出用户草稿中所有需要重写的位置。
```

### P2.6 理论谱系表 · 产出 (theory)
**Trigger:** theory paper Stage 2 · **Produce**
```
围绕【核心概念/理论】梳理理论谱系。按以下字段输出结构化表格：
代表学者 | 时期 | 核心命题 | 理论贡献 | 局限 | 与本文问题的关系

之后总结：
- 学派分化：哪些学者站在哪一侧？
- 主要争议：核心争议点是什么？
- 可进入的理论缺口：本文最适合切入哪个争议？
```

## Stage 3 — 假设 / 论证入口 / 阐释视角

### P3.1 四层假设架构 · 产出 (empirical / methods)
**Trigger:** Stage 3 for empirical / methods · **Produce**
```
围绕【研究对象】与【核心方法】，构建四层假设：
- 机制假设 (H1)：为什么该效应/关系应该存在？
- 性能假设 (H2)：预期方向和量级？
- 泛化假设 (H3)：在什么条件下依然成立？
- 边界假设 (H4)：在什么条件下会失效？为什么？

每条假设写清：理论依据 · 可观测变量 · 需要的对照组 · 计划统计检验 · 什么证据支持、什么证据反驳。
所有假设必须能被用户手上的真实数据推翻。
```

### P3.2 因果链条图 · 产出
**Trigger:** empirical paper needs identification story · **Produce**
```
画出"概念 → 机制 → 变量 → 假设"的文字版因果链条：
- 明确 IV / DV / mediator / moderator / control
- 每条箭头标注理论依据
- 标出潜在混杂 / 内生性 / 反向因果风险
- 说明本设计如何识别 (RCT / DiD / IV / RDD / matching / 面板固定效应)
```

### P3.3 假设可检验性审计 · 审计
**Trigger:** post-produce Stage 3 audit · **Audit**
```
审查【假设列表】的可检验性。逐条检查：
1) 变量能否被精确测量、编码或从材料识别？
2) 是否遗漏关键控制变量 / 混杂因素？
3) 是否存在内生性 / 反向因果漏洞？
4) 假设能否直接指导下一阶段的实验设计和基线选择？
5) 每条假设是否有具体证据能反驳它？(不能反驳的假设不是假设)

将无法直接检验的命题改写为带具体测量指标的可检验版本。
```

### P3.4 论证入口 · 产出 (theory / interpretive)
**Trigger:** theory / interpretive Stage 3 · **Produce**
```
根据【理论争议 / 阐释对象】，提炼 3 种可能的论文主论点。每种论点说明：
- 批判 / 修正 / 整合的对象
- 论证路径（要经过哪几层推理）
- 可能贡献 (概念修正 / 理论整合 / 新框架 / 新解释)
- 潜在反驳 + 应对策略
- 需要哪些原文 / 材料 / 案例来支撑
```

## Stage 4 — 研究设计 / 实施路径 / 论证框架 / 分类框架 / 细读

### P4.1 防泄漏数据划分 · 产出 (empirical / methods)
**Trigger:** Stage 4 for empirical / methods · **Produce**
```
为【任务/数据类型】设计防泄漏数据预处理与划分方案：
- 异常值处理规则
- 缺失值策略
- 严格划分策略 (请从以下选择并说明防的是什么泄漏)：
  · 患者/主体级划分
  · 跨中心/跨设备划分
  · 时序划分
  · Group k-fold
  · 冷启动划分
- 图像/文本标准化：均值方差只用训练集估计
- 数据字典 + 版本控制方式

每一步都名指它防的是哪种泄漏（target / temporal / patient / pretraining-corpus overlap / distribution shift）。
```

### P4.2 阶梯式基线 · 产出
**Trigger:** designing baselines · **Produce**
```
为【方法/任务】设计阶梯式基线体系，至少包含：
1) 平凡基线 (majority class / linear / rule-based)
2) 传统机器学习基线
3) 经典 AI 基线 (代表性网络)
4) 当前 SOTA 强基线
5) 消融版本 (去掉本文关键模块)

每个基线说明：参数量、训练轮数、超参搜索预算、随机种子、公平训练原则。
明确"你不能只对比几年前的旧模型"。
```

### P4.3 消融矩阵 · 产出
**Trigger:** designing ablations · **Produce**
```
为【模型/方法】设计消融实验矩阵：
消融编号 | 移除/替换的模块 | 验证的假设 | 预期方向 | 评价指标 | 图表呈现方式

强制：每个消融必须绑定到 Stage 3 的一条假设。任何不能绑定假设的消融是"装饰性消融"，删除或重设计。
```

### P4.4 Reviewer-2 打击清单 · 审计
**Trigger:** post-produce Stage 4 audit · **Audit**
```
以极度挑剔的 Reviewer 2 视角审查【实验设计】。硬指标：
1) 隐藏数据泄漏路径？(target / temporal / patient / pretraining-corpus overlap / normalization leakage)
2) 基线胜之不武？(不平衡数据只报 Accuracy 无 AUC/F1 / 只对比旧模型 / 不公平算力或调参预算)
3) 消融缺失、冗余、无法解释？
4) 稳健性检查够吗？(数据扰动 / 指标替换 / 外部验证 / 种子方差)
5) 样本量是否有 power 分析？

输出：致命漏洞清单 + "最小修改、最大可信度"的补充实验方案 + 验收结论。
```

### P4.5 章节论证任务表 · 产出 (theory)
**Trigger:** theory Stage 4 · **Produce**
```
根据【核心论点】设计论文章节结构：
章节 | 承担的论证任务 | 使用的理论材料 | 与主论点的关系 | 可能反驳位置

约束：
- 每章只解决一个子问题
- 不允许"文献介绍"章节冒充"理论论证"章节
- 反驳必须以对方最强版本出现，不能稻草人
```

### P4.6 编码方案 · 产出 (review / interpretive)
**Trigger:** review / interpretive Stage 4 · **Produce**
```
为【文献/材料集】设计编码方案：
字段名 | 定义 | 取值范围 | 编码示例 | 与研究问题的对应
+ 编码员培训要点
+ 一致性评估方法 (Cohen's kappa / Krippendorff's alpha / Dice / IoU 等)
+ 分歧仲裁规则
+ 编码日志模板
```

## Stage 5 — 数据分析 / 效果验证 / 论证展开 / 评价 / 阐释

### P5.1 统计不确定性报告 · 产出
**Trigger:** results write-up · **Produce**
```
根据【实验结果】撰写结果段，硬性要求：
- 除 p 值外，必须报告效应量 + 95% 置信区间
- 多重比较是否做校正？(Bonferroni / BH-FDR / Holm)
- 若比较 AUC：用 DeLong 检验
- 若配对比较：McNemar
- 若小样本或分布未知：bootstrap
- 图表：不用截断轴、不用双轴、每张图有独立可读的标题

每条推论都要指向一个具体数字（不是"效果好"，而是"AUC 0.91 vs 0.86，DeLong p=0.03"）。
```

### P5.2 失败案例分析 · 产出
**Trigger:** discussion of limitations / errors · **Produce**
```
按以下维度分析【模型/方法】的失败案例：
1) 数据质量维度：低信噪比 / 噪声标签 / 采集偏差
2) 边界样本维度：小目标 / 罕见类别 / 极端条件
3) 模型结构维度：容量瓶颈 / 感受野 / 输入模态不足
4) 任务定义维度：标签模糊 / 类别边界不清

每一维度：典型样本 + 归因解释 + 改进方向。
拒绝为结果辩解 —— 诚实的失败分析比虚假的"效果显著"更有价值。
```

### P5.3 过度推断审计 · 审计
**Trigger:** results/discussion audit · **Audit**
```
审查【结果/讨论段落】。硬指标：
1) 是否把相关性写成了因果？
2) 结论是否超出测试分布外推？
3) 图表是否视觉误导 (截断轴 / 双轴 / 冗余面板 / 遮蔽异常值)？
4) 单次实验的结果是否被叙述为稳定发现？(需要多种子/多划分证据)

每条过度推断都必须：
- 引用具体过度句
- 说明数据支撑到什么程度
- 给出克制的改写版
```

### P5.4 证据链审计 · 审计 (interpretive)
**Trigger:** interpretive paper Stage 5 audit · **Audit**
```
审查【阐释段落】。硬指标：
1) 每一处解释是否可以回到具体文本页码/档案编号？
2) 是否存在只选择支持解释的段落 (cherry-picking)？
3) 理论视角是否压过了文本，让材料被迫符合理论？
4) 是否呈现了文本的复杂性和内部张力，还是把文本简化为一个主题？

对任何"因为文本中说 X，所以意味着 Y"的推断，追问：这个推断需要多少步？每一步的合法性？
```

## Stage 6 — 写作

### P6.1 三层润色 · 产出
**Trigger:** user provides a paragraph to polish · **Produce**
```
对【段落文本】做三层修改：
- 第一层 · 逻辑：重组为漏斗式或递进结构；补全断裂的因果链；补上引言埋的坑。
- 第二层 · 学术表达：删掉"完美解决 / 效果显著 / state-of-the-art / significantly outperforms"这类无检验的营销词；替换为"与基线相比更稳定 / 该模块旨在缓解..."。
- 第三层 · 精简：压缩重复；加强句间逻辑连接词；术语首次出现规则 (中文+English abbreviation)。

输出：修改后文本 + 修改理由对照表 (原文 → 改后 → 理由)。
```

### P6.2 摘要重构 · 产出
**Trigger:** abstract rewriting · **Produce**
```
根据【背景 / 目的 / 方法 / 结果 / 结论】写结构化摘要。硬性要求：
- 突出研究空白 (一句话说清"以前没做好的是")
- 说明数据规模、对照方法、核心指标数值
- 报告置信区间或稳定性证据
- 结论不超出数据支持范围
- 拒绝"取得了良好效果"这类空话

输出后再问自己：编辑读完摘要能否用一句话说出这篇论文做了什么、结果多强、为什么重要？如果不能，重写。
```

### P6.3 引言漏斗 · 产出
**Trigger:** introduction draft · **Produce**
```
按四段漏斗写引言：
第 1 段：现实/科学问题 (为什么这个问题值得研究)
第 2 段：已有研究进展 (领域走到了哪里)
第 3 段：关键不足 (哪个具体缺口 → 埋下方法必要性)
第 4 段：本文贡献 (回应缺口的方式 + 3–4 条可验证贡献 + 论文结构)

每段有中心句和过渡句，每处主张都指向需要引用的文献类型（不是具体文献名）。
```

### P6.4 论文闭环审计 · 审计
**Trigger:** post-Stage 6 audit · **Audit**
```
论文逻辑一致性审查。硬指标：
1) 引言提出的问题 → 方法真的在解决 → 结果有数据证明 → 结论有明确回答？逐环追踪。
2) 术语 / 指标名称 / 缩写从头到尾统一？(列出不统一的位置)
3) 讨论的"升华"是否超出结果能支撑的极限？(列出所有超范围表述)
4) 每章开头/结尾的过渡句是否完成"承前+启后"？

输出：高风险 / 中风险 / 低风险问题清单，每条指向精确位置。
```

## Stage 7 — 终稿 / 投稿 / 审稿回复 / 答辩

### P7.1 标题重塑 · 产出
**Trigger:** title improvement · **Produce**
```
为【论文】生成 4 版标题：
- 保守型：只描述对象和方法
- 方法型：突出方法创新点
- 应用型：突出场景和价值
- 高影响型：突出发现或贡献强度 (不夸大)

每版说明：适合投向哪类期刊 / 会议、可能被审稿人质疑的点、如何在摘要中兑现标题承诺。
拒绝"AI 赋能 XX"式口号。
```

### P7.2 审稿意见拆解 · 产出
**Trigger:** user has reviewer comments · **Produce**
```
把【审稿意见】按以下四类拆解：
- 必须修改 (若不改会拒稿)
- 建议修改 (会强化论文)
- 需澄清 (审稿人误解)
- 无法完成但需解释 (超出本文范围)

每条意见追问："审稿人字面上说 X，但背后真正的担忧是什么？"—— 通常是：
- 强基线不足
- 统计不严谨
- 结论过度
- 外部验证缺失
- 期刊匹配度问题
- 理论立场不清

按"字面意见 → 真实关切 → 应对策略 (Response / Revision / Location)"输出。
```

### P7.3 逐条回复模板 · 产出
**Trigger:** writing rebuttal · **Produce**
```
针对【审稿意见 X】，按以下三段结构写回复：

Response：感谢审稿人指出，我们同意/部分同意/需澄清 ... (态度诚恳，不防御)
Revision：我们已 (新增/修改/删除) ... 具体动作是 ...
Location：见修改稿第 §<章节>，页 <页码>，表 <编号>，图 <编号>。

避免："we thank the reviewer for the insightful comments"式空话开头 → 换成对具体问题的直接回应。
避免：把审稿人当成不懂的人 → 假设审稿人是领域内专家。
```

### P7.4 最小最有说服力补充实验 · 产出
**Trigger:** deciding what supplementary experiments to add · **Produce**
```
根据【审稿意见】设计"最小修改、最大说服力"的补充实验：
- 优先级 1：直接回应审稿人质疑（通常是外部验证 / 强基线 / 泛化实验）
- 优先级 2：审稿人隐含要求的（例如提到"泛化"→ 隐含要外部数据集）
- 优先级 3：主动补的稳健性（种子方差 / 指标替换）

每个补充实验：需要多少时间、预期结果 (含结果不理想时的应对话术)、能塞入正文还是附录。
避免：盲目加大量新实验；给审稿人错觉"我们做了很多但没回答你的问题"。
```

### P7.5 数据/代码可用性声明 · 产出
**Trigger:** open-science section · **Produce**
```
根据【开放程度 / 隐私限制 / 仓库地址】写数据与代码可用性声明：
- 可公开：<清单>
- 需申请：<清单 + 联系方式 + 审批流程>
- 因伦理/版权/敏感性不能公开：<清单 + 原因 + 替代方式，如脱敏样例、合成数据>
- 环境：Python/框架版本、随机种子、硬件、许可证
- 复现指南入口 (README 位置)
```

### P7.6 Technical Check bot · 审计
**Trigger:** pre-submission final check · **Audit**
```
以无情的 Technical Check bot 视角对照【目标期刊/学校要求】做终极排查。硬指标：
1) 利益冲突声明、IRB / 伦理审批、数据/代码开源链接 (或脱敏说明) —— 齐备否？
2) 图表编号连续、正文全部引用、附录条目对齐 —— 有任何 orphan？
3) 摘要 / 结论中的每一个数字与结果部分零误差对齐？(逐字核对)
4) 参考文献格式完全统一？无过时/自引过多/引用与论断不匹配？
5) 目标期刊字数/图数/结构模板 —— 全部满足？

若存在缺失，输出"不可提交警告列表 (Do-Not-Submit List)"，每条给出精确位置和必须修改内容。不允许输出任何鼓励性话语。
```

### P7.7 答辩 20 问预演 · 产出
**Trigger:** thesis defense prep · **Produce**
```
以答辩委员会视角针对【论文题目/摘要】提出 20 个最尖锐的问题，覆盖：
- 选题意义 (5 问)：为什么这个问题重要？为什么现在？为什么是你？
- 方法与创新 (5 问)：为什么不用更简单的方案？创新点相对于 X 是什么？
- 数据与实验 (5 问)：数据量是否足够？基线是否公平？外推到 X 场景成立吗？
- 局限与应用 (5 问)：主要局限？如何影响结论？下一步怎么做？

每个问题附：
- 一句话直答（有证据、不过度承诺）
- 主动引回论文贡献
- 若被追问，进一步的备答
```

### P7.8 跨学科价值表达 · 产出
**Trigger:** paper is technical but audience is domain (e.g. AI+医学) · **Produce**
```
把【技术研究】翻译为【应用领域】读者关心的贡献：
- 技术指标 → 领域含义：例如 AUC +0.05 → 减少 X% 漏诊、节省 X 分钟标注、降低 X% 误报
- 方法特性 → 领域可行性：例如轻量化 → 可部署到基层医院/边缘设备
- 局限 → 领域风险：例如样本仅覆盖 2 家中心 → 结论仅适用于相近人群

拒绝在技术层面反复重申"性能高"—— 必须给出领域可感知的具体量化含义。
```

## 高频通用工具 (Cross-stage)

### U.1 术语一致性 · 审计
```
检查【全文】的术语统一性：
- 同一概念的不同叫法 (中/英/缩写)
- 首次出现规则 (中文名 (English full name, ABBR))
- 后续出现规则
- 指标名称 / 模型名称 / 数据集名称的规范拼写

输出统一术语表 + 需要替换的位置清单。
```

### U.2 局限性重写 · 产出
```
根据【研究设计和结果】写真实、具体、不削弱贡献的局限性：
- 避免："样本量有限、未来需要更多数据"这类模板句
- 每条局限给出：具体来源 (设计/数据/方法/评价) + 对结论的具体影响 + 改进方向
- 通常 3–5 条即可，多则显得心虚
```

### U.3 复现材料清单 · 产出
```
为【论文】列复现材料清单：
- 代码仓库 + 版本 tag + README
- 数据说明 (原始 / 处理后 / 划分索引 / 授权状态)
- 环境 (框架版本 / CUDA / 硬件)
- 随机种子与训练脚本
- 模型权重
- 实验日志与结果表 CSV
- 许可证
- 联系方式与申请流程 (若受限)
```

## Usage guidance

- Use these as scaffolding, not verbatim copy — fill placeholders from the user, tailor to their field.
- Chain them: e.g. P2.3 (evidence matrix) → P2.4 (gap audit) → P3.1 (four-layer hypothesis).
- If a prompt in this library conflicts with what the user has already told you, follow the user. Prompts are defaults, not constraints.
- When you write the audit response, always finish with the 6-part template from `acceptance_templates.md` — the atomic prompts above produce content, not verdicts.
